\section{Desarrollo}

El desarrollo del sistema de inicio de sesión se realizó en lenguaje C, utilizando la biblioteca \texttt{ncurses} para construir una interfaz de usuario basada en texto y la biblioteca \texttt{libsodium} para el procesamiento de contraseñas.
El sistema permite registrar cuentas, autenticar usuarios y conservar la información necesaria entre ejecuciones.
Para organizar estas operaciones, la implementación se dividió en módulos que separan la lógica de autenticación, los componentes visuales y el flujo principal, lo que permite distinguir las responsabilidades de cada parte del programa.

\subsection{Organización del código fuente}

El proyecto se organiza en varios archivos fuente y de cabecera, cada uno con una responsabilidad definida dentro de la aplicación.
El archivo \texttt{main.c} contiene el flujo principal y coordina las operaciones de inicio de sesión y registro, mientras que \texttt{auth.c} implementa las funciones relacionadas con la autenticación, la validación de credenciales y el manejo de la información persistente.
Por su parte, \texttt{auth.h} declara las interfaces del módulo de autenticación, y los archivos \texttt{ui.c} y \texttt{ui.h} contienen las funciones y declaraciones relacionadas con la presentación de formularios, mensajes y opciones mediante \texttt{ncurses}.
Finalmente, el archivo \texttt{Makefile} reúne las instrucciones necesarias para compilar y enlazar el programa.

La separación entre autenticación e interfaz mantiene diferenciadas las operaciones que procesan las credenciales y aquellas que presentan los formularios y mensajes en pantalla.
El archivo principal coordina ambos módulos para establecer el flujo de navegación de la aplicación, mientras que las interfaces declaradas en los archivos de cabecera permiten conectar las funciones entre sí de manera organizada.

\subsection{Compilación del programa}

La compilación se administra mediante un archivo \texttt{Makefile}, que reúne las opciones del compilador, los archivos fuente y las bibliotecas requeridas por el proyecto \cite{make}.
Para generar el ejecutable se utiliza GCC con el estándar C11 y opciones de advertencia como \texttt{-Wall}, \texttt{-Wextra} y \texttt{-Wpedantic}, que ayudan a identificar posibles errores y construcciones que no se ajustan al estándar seleccionado.
La opción \texttt{-O2} aplica optimizaciones al código generado.

El programa requiere las bibliotecas \texttt{ncurses}, \texttt{tinfo} y \texttt{sodium}.
Las bibliotecas relacionadas con \texttt{ncurses} proporcionan las funciones necesarias para trabajar con la terminal, mientras que \texttt{libsodium} incorpora las operaciones criptográficas empleadas para procesar las contraseñas.
Estas dependencias deben estar disponibles en el entorno para que el proceso de compilación pueda completarse correctamente.

La compilación del proyecto se inicia desde el directorio que contiene el archivo \texttt{Makefile} mediante el comando siguiente:

\begin{center}
    \texttt{make}
\end{center}

Cuando la compilación finaliza correctamente, se genera el ejecutable \texttt{acceso}, que puede iniciarse desde el mismo directorio mediante el comando siguiente:

\begin{center}
    \texttt{./acceso}
\end{center}

\subsection{Implementación de la interfaz con ncurses}

La interfaz de usuario se desarrolló mediante la biblioteca \texttt{ncurses}, que permite controlar la presentación de texto, la posición del cursor y la lectura de entradas del teclado dentro de una terminal \cite{stevens2013}.
Su utilización hace posible organizar los formularios y los mensajes de la aplicación sin recurrir a una interfaz gráfica tradicional, manteniendo la interacción dentro del entorno de consola.

La pantalla principal presenta las opciones relacionadas con el acceso y el registro de cuentas, y los campos de entrada se representan visualmente como cuadros de texto.
Las opciones seleccionadas se distinguen mediante resaltados de color, mientras que la combinación de fondo oscuro y texto claro mantiene una presentación uniforme en las distintas pantallas.

La navegación se realiza mediante las teclas de dirección, \texttt{ENTER} y \texttt{ESC}.
Las teclas de dirección permiten desplazarse entre las opciones disponibles, \texttt{ENTER} confirma la selección o permite continuar con una operación y \texttt{ESC} permite regresar o cancelar la acción correspondiente de acuerdo con el contexto de la interfaz.
La configuración de \texttt{ncurses} incluye funciones como \texttt{noecho()}, que evita que la entrada se muestre automáticamente en pantalla, y \texttt{keypad()}, que permite interpretar teclas especiales según la configuración del terminal \cite{stevens2013}.
Estas funciones centralizan la interacción con el teclado y contribuyen a mantener un comportamiento consistente entre las pantallas de autenticación y registro.

\subsection{Registro de usuarios y validación de datos}

El registro permite crear nuevas cuentas mediante un nombre de usuario, una dirección de correo electrónico y una contraseña con su respectiva confirmación.
Antes de almacenar una cuenta, el sistema verifica que los datos ingresados cumplan con las reglas de validación definidas para el proyecto, con el propósito de evitar registros incompletos, duplicados o incompatibles con los requisitos establecidos.

El nombre de usuario debe contener al menos cinco caracteres y no debe encontrarse registrado previamente, lo que evita el uso de identificadores demasiado cortos y permite mantener su unicidad.
De manera similar, la dirección de correo electrónico debe presentar una estructura válida y no estar asociada a otra cuenta.
Esta comprobación revisa la sintaxis de la dirección proporcionada, pero no confirma que el buzón exista ni que el usuario tenga acceso a él.

La contraseña debe cumplir con los requisitos de complejidad establecidos, que incluyen letras mayúsculas, letras minúsculas, números y símbolos.
Además, el sistema solicita una segunda entrada para confirmar la contraseña y ambas entradas deben coincidir para que el registro pueda continuar.
Cuando un campo no cumple con las reglas correspondientes, el flujo de registro permite corregir la entrada inválida sin perder los valores válidos que ya se habían introducido en los demás campos.

\subsection{Protección de contraseñas y autenticación}

El tratamiento de las contraseñas es una parte esencial del sistema, ya que estos datos se utilizan para comprobar la identidad de los usuarios.
Por esta razón, la aplicación emplea las funciones criptográficas de \texttt{libsodium} para generar y verificar hashes de contraseñas mediante el algoritmo Argon2id, evitando que la contraseña original tenga que conservarse directamente en el archivo de usuarios \cite{libsodium}.

Durante el registro, la función \texttt{crypto\_pwhash\_str()} genera una representación criptográfica destinada al almacenamiento e incorpora los parámetros necesarios para verificar la contraseña posteriormente.
Durante el inicio de sesión, el sistema busca el registro correspondiente al nombre de usuario y utiliza \texttt{crypto\_pwhash\_str\_verify()} para comprobar la contraseña ingresada frente al hash almacenado.
La autenticación se considera correcta cuando la cuenta existe y la verificación criptográfica confirma que la contraseña proporcionada es válida.

El comportamiento de la interfaz depende del resultado de esta validación.
Cuando la contraseña es incorrecta, el campo correspondiente se limpia para permitir una nueva entrada, mientras que el nombre de usuario se conserva; si el nombre de usuario no existe, se limpian ambos campos para que el siguiente intento comience con los datos de acceso vacíos.
Argon2id se utiliza para la verificación de contraseñas mediante hashes y no equivale al cifrado reversible, ya que el sistema no necesita recuperar la contraseña original.

Adicionalmente, las funciones de limpieza de memoria de \texttt{libsodium}, como \texttt{sodium\_memzero()}, permiten borrar explícitamente determinados datos sensibles de los búferes utilizados por el programa cuando corresponde.
Esta medida complementa el manejo de credenciales al reducir el tiempo durante el cual ciertos datos permanecen en memoria.

\subsection{Registro y persistencia en archivos}

La información de las cuentas se conserva en un archivo local denominado \texttt{usuarios.txt}, lo que permite mantener los registros entre ejecuciones sin requerir un sistema gestor de bases de datos ni una conexión a un servidor remoto. El uso de archivos como mecanismo de persistencia requiere considerar las operaciones de lectura y escritura, así como los permisos de acceso y la protección de la información almacenada \cite{tanenbaum2009,stevens2013,kerrisk2010}.
Los datos se almacenan en registros delimitados por dos puntos, con el nombre de usuario, el correo electrónico y el hash de la contraseña, de acuerdo con la estructura siguiente:

\begin{center}
    \texttt{usuario:correo:hash}
\end{center}

En esta estructura, el primer campo corresponde al nombre de usuario, el segundo contiene la dirección de correo electrónico y el tercero almacena el hash generado para la contraseña.
Por lo tanto, la contraseña original no forma parte del registro persistente.
La lectura del archivo permite localizar las cuentas existentes y recuperar la información necesaria para comprobar la unicidad del nombre de usuario y del correo electrónico, así como para realizar la autenticación.

Cuando se registra una nueva cuenta, la información correspondiente se incorpora al archivo para que permanezca disponible después de cerrar y volver a ejecutar el programa.
Este enfoque evita depender de servicios externos para las operaciones básicas del sistema, aunque la disponibilidad y la integridad de los registros siguen dependiendo de los permisos, el estado y la administración del archivo en el equipo donde se ejecuta la aplicación.
El almacenamiento de hashes reduce la exposición directa de las credenciales, pero no elimina la necesidad de proteger el archivo y el entorno de ejecución.

Los escenarios anteriores abarcan las operaciones principales del sistema y permiten distinguir los resultados de un registro válido de aquellos producidos por entradas incorrectas.
La comprobación de estos comportamientos permite evaluar la correspondencia entre las reglas de negocio, la lógica de autenticación y la interacción presentada en la terminal.

Los resultados observados durante las pruebas deben interpretarse de acuerdo con las condiciones de cada escenario.
En particular, el registro correcto debe conservar la cuenta en el archivo local, mientras que los datos inválidos deben impedir la creación de registros que incumplan las reglas establecidas.
De forma equivalente, el inicio de sesión debe permitir el acceso únicamente cuando la cuenta existe y la contraseña supera la verificación criptográfica.

La persistencia se evalúa mediante la disponibilidad de los registros después de finalizar y volver a iniciar la aplicación, mientras que las pruebas de navegación permiten comprobar que los controles del teclado mantienen el comportamiento previsto en las distintas pantallas.
En conjunto, estos escenarios describen los aspectos funcionales esenciales de la aplicación, sin sustituir las comprobaciones específicas de seguridad, concurrencia o resistencia ante modificaciones externas del archivo de usuarios.
